# Аудит сборки, доставки и границ сообщений

Дата: 23 сентября 2026. Проверялся текущий рабочий снимок ветки `codex/full-audit-2026-09-23`, включая уже имеющиеся изменения пользователя. Production-файлы не изменялись; сборка в основном дереве не запускалась.

## Подтвержденные проблемы

### BS-01 — P1: перехват fetch может навсегда задержать ответ сайта

**Места:** `src/main.js:1061`, `src/main.js:1072–1097`, `src/apiManager.js:172–190`, `src/main.js:1233–1242`.

Перехватчик отправляет на обработку любой ответ `image/*`, кроме URL, содержащих `maps` или `openfreemap`. Однако получатель отвечает только на endpoint `tile`/`tiles`. Например, обычный `fetch('/assets/avatar.png')` с успешным PNG-ответом попадает в Promise, который никто не завершит. Условие определяется Content-Type, поэтому это относится именно к загрузкам через `fetch`; обычные теги `<img>` этим воспроизведением не охвачены.

Та же проблема возникает для настоящего тайла, если `drawTemplateOnTile` отклоняется: `apiManager.js:182` не перехватывает ошибку и не отправляет оригинальное изображение обратно. `.catch` у Promise в `main.js:1098` этого не исправляет — обработчик работает в отдельном событии, а Promise не получает `reject`. Тайм-аута, отмены и fallback нет. Запись остается в `fetchedBlobQueue` вместе с замыканием ответа. Во время импорта шаблонов слушатель устанавливается только после `await importJSON`, что создает еще одно окно потери сообщений.

**Результат:** загрузка ресурса/тайла сайта остается незавершенной до перезагрузки; событие завершения обновления также не поступает. На картах это проявляется отсутствующим тайлом и незавершенным обновлением. Ошибка декодирования одного изображения не должна лишать сайт успешного оригинального ответа.

**Воспроизведение:** `node audit/2026-09-23/build-security/repro.mjs` исполняет извлеченные из исходников fetch-hook и `ApiManager`, с fake original fetch и изолированной очередью сообщений. Контрольный тайл завершается; non-tile PNG остается pending и renderer не вызывается; тайл с отклоненным renderer остается pending с зафиксированной ошибкой. Окно наблюдения — 150 мс; отсутствие последующего пути завершения дополнительно проверено по исходному коду.

**Исправление:** перехватывать только явно разрешенные URL тайлов; установить consumer до длительного импорта; иметь timeout/AbortSignal и возврат оригинального ответа при отказе renderer; очищать очередь в каждом терминальном состоянии.

### BS-02 — P1: сообщение коммита исполняется как shell-код в CI с правами записи

**Места:** `.github/workflows/build.yml:128–155`, `.github/workflows/build.yml:182`; полномочия `.github/workflows/build.yml:34–35`, `.github/workflows/build.yml:161–162`.

TITLE/BODY считываются из сообщения коммита, после чего GitHub expressions вставляют их непосредственно внутрь кавычек shell-команды `git commit`. Кавычки не запрещают командную подстановку `$()`/backticks. Название коммита `Fix documentation $(printf CI_INJECTION_PROOF >&2)` исполняет вложенную команду в runner. Такой текст также может случайно встречаться в техническом сообщении коммита.

**Результат:** если контролируемый автором текст попадает в сообщение коммита, запустившего workflow на `main`, shell выполняет его с полномочиями job. Здесь job имеет `contents: write`, а Git credentials настроены для записи в репозиторий. Это не утверждение, что любой открытый PR автоматически получает секреты: требуется попадание контролируемого сообщения в `main` и запуск этого workflow.

**Воспроизведение:** тест берет фактическую строку workflow, подставляет безвредный title и запускает Bash с функцией-заглушкой `git`. В stderr появляется `CI_INJECTION_PROOF`, при этом настоящие git-команды и сетевые операции не выполняются. То же место присутствует в merge job.

**Исправление:** передавать TITLE/BODY через переменные окружения и использовать `"$TITLE"`/`"$BODY"` внутри shell; для многострочных данных предпочтителен файл сообщения. Не делать промежуточную обратную подстановку `${{ env.TITLE }}` прямо в `run:`. Это соответствует [официальной рекомендации GitHub по script injections](https://docs.github.com/en/actions/concepts/security/script-injections).

### BS-03 — P3: обработчики сообщений читают payload до проверки типа

**Места:** `src/main.js:51–52`, `src/apiManager.js:64–70`, `src/apiManager.js:78`.

`window.postMessage(null, ...)` допустим, но первый обработчик сразу деструктурирует `event.data`, а второй читает `data['jsonData']` раньше проверки `data`. Оба бросают TypeError на сообщении, не предназначенном для Chromora. У endpoint также не проверяется строковый тип до `.split`.

**Результат:** лишние необработанные ошибки/отклонения Promise при совместной работе с другими скриптами или iframe. Само воспроизведение не доказало остановку дальнейших событий или всего интерфейса; такой ущерб здесь не заявляется.

**Воспроизведение:** тот же `repro.mjs`: `data: null` дает две ожидаемые TypeError, записанные в `repro-results.json`.

**Исправление:** до деструктурирования проверить `event.data != null`, объектный тип, `source`, типы endpoint/blobID/blobData; возвращать управление для чужих сообщений.

## Граница доверия: подтвержденное отсутствие валидации, эксплуатация браузера не проверена

`src/apiManager.js:64–78` не проверяет `event.source`/`event.origin`; page blob-listener `src/main.js:51–72` также этого не делает. В отличие от них, paint-area listener уже содержит обе проверки (`src/main.js:902`).

В тесте синтетическое событие с чужим origin, чужим source и payload `source: 'blue-marble', endpoint: '/api/me'` успешно изменило `templateManager.userID` на `123456`. Это подтверждает прием чужого сообщения на уровне обработчика. Практический внешний сценарий потребовал бы, чтобы чужая страница имела ссылку на окно/iframe Wplace и политика изоляции сайта допускала сообщение. COOP/CSP и реальный foreign-origin popup не проверялись. **Не заявляются** XSS, кража учетных данных или доступ к GM storage. События с той же страницы принципиально не аутентифицируются одним лишь сравнением origin/source.

Рекомендация: перенести проверки `source === window` и origin в общую границу приема, проверять схему payload и ограничивать разрешенные endpoint/операции. Значения ID/координат должны быть конечными допустимыми числами до изменения состояния.

## Доставка и сопровождение: отдельные риски, не выданы за воспроизведенные production-инциденты

1. `.github/workflows/build.yml` использует общие ветки `auto`/`wiki` и force-reset без concurrency. `update-auto` берет актуальный `origin/main` (`:28`), тогда как build checkout берет commit конкретного события (`:48`). При пересекающихся push возможны несовместимые родители коммитов, non-fast-forward при `:156` и подмена общей `origin/auto` другим запуском перед merge (`:181`). Нужны сериализация publication jobs и привязка артефакта/коммита к SHA запуска; лучше передавать artifact, а не использовать общую изменяемую ветку как очередь.
2. Build workflow запускается только на push в main (`:3–6`); `package.json:10–12` не содержит test/lint scripts. CodeQL есть на PR, но он не заменяет сборку userscript и проверку page/sandbox contracts. Ошибки сборки выявляются после merge.
3. Release build делает `npm install` (`build.yml:56`), тогда как `npm ci` дает проверку соответствия lockfile. Генерация документации дополнительно выполняет `npm install minami taffydb` (`:212`), что допускает незапланированный дрейф этого окружения.
4. Terser mangles почти все незаключенные в кавычки свойства (`build/build.js:137–149`), в том числе имена сохраненных полей `colorLayout` → `xi` и `layoutSizes` → `Ci`. Сейчас есть allowlist контрактов, но ее пополнение вручную не проверяется тестами на готовом bundle. **Дополнительная проверка не подтвердила текущую несовместимость:** working dist, clean local build, clean CI build и пять исторических dist из Git (релизы 1.1.0, 1.2.0, 1.3.0) используют одни и те же `xi`/`Ci`; извлеченные реальные getter-функции корректно читают горизонтальный режим и сохраненную геометрию между всеми проверенными сборками. Поэтому отдельный P2-баг сброса этих настроек не заявлен. Это остается риском будущей смены mapping; полезны стабильные имена persisted keys и smoke-тесты именно minified userscript, включая `postMessage`, service worker, MapLibre и сохраненные данные между двумя сборками.
5. CSS mangler ищет все строки с `bm-`, а не только CSS-селекторы (`build/cssMangler.js:140–163`): в карте есть также `bm-last-me`, `bm-revision`, `bm-name`. Это размывает границу между оформлением и протоколом. Сам по себе текущий проход не доказал несовпадение JS/CSS; это риск дальнейших изменений, а не подтвержденный визуальный дефект.
6. Userscript ограничен `https://wplace.live/*`, содержит `@noframes` и не запрашивает общий привилегированный HTTP API. Сам userscript включает CSS и Roboto Mono, но еще подключает Google Fonts для Michroma/Rajdhani (`src/main.js:1144`); поэтому утверждение о полной независимости от внешних ресурсов требует оговорки про шрифты.

## Что проверено без подтвержденной уязвимости

- DOM-вывод названий шаблонов в `WindowTemplates` выполняется через textContent. Счетчики `/me` проходят `Intl.NumberFormat` до innerHTML. На просмотренных путях подтвержденного XSS нет.
- Imported tiles декодируются как Blob/image bitmap, а не исполняются через eval/Function. На просмотренных путях подтвержденного исполнения импортированного кода или глобального prototype pollution нет.
- Запись шаблонов перечитывает актуальное хранилище и защищает непризнанную схему/испорченный JSON от перезаписи (`templateManager.js:697–725`); это положительное свойство. Схема содержимого и размер декодируемых изображений требуют отдельной проверки функциональности и производительности.
- Активной телеметрии в просмотренных исходниках не найдено; есть очистка старых `telemetry`/`uuid` из настроек.
- npm audit, clean builds и размеры артефактов собираются основным аудитом отдельно и здесь не дублировались.

## Артефакты и ограничения

- `repro.mjs` — повторяемые тесты фактических исходных обработчиков и workflow-line; DOM, original fetch и renderer изолированы заглушками.
- `repro-results.json` — фактические результаты Node v25.8.0 на Windows.
- `check-storage-mangling.mjs`, `storage-mangling-results.json` — AST-проверка actual bundle и выполнение извлеченных getter-функций при переносе настроек между сборками; обнаруженный mangling не привел к потере этих двух полей в восьми проверенных переходах.
- Реальный Wplace backend, установка Tampermonkey/Violentmonkey и запускаемые GitHub Actions этим набором не затрагивались. Нет утверждения о полноценном end-to-end тесте браузера или успешной удаленной атаке.
