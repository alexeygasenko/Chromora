# Исправления после проверки в браузере

23 сентября 2026. Проверена существующая вкладка Wplace в Brave с Tampermonkey.

В консоли подтверждены две ошибки: `Chromora: Could not fetch userdata. HTTP 404` и `The message catalog was used before initializeLocale() completed`. Окна Chromora присутствовали, счетчики оставались нулевыми, canvas карты отсутствовал.

## Причины и изменения

1. Запрос данных пользователя отправлялся на `https://wplace.live/api/me`, тогда как текущий публичный клиент Wplace использует `https://backend.wplace.live/me`. Также строгий allowlist не пропускал backend API без префикса `/api`. Исправлены прямой запрос и оба обработчика сообщений/ответов. Origin, пути, типы данных и источник сообщений продолжают проверяться. Ответ 401 обрабатывается как обычный режим посетителя без входа.
2. Добавленная при аудите инвалидация после первоначального импорта шаблонов слишком рано запускала обнаружение runtime. Оно импортировало предварительно загруженные модули Wplace до готовности переводов. Ошибка оценки ES-модуля сохраняется в кеше модулей текущей страницы и мешает последующей загрузке самого сайта. Теперь обнаружение ждет появления `canvas.maplibregl-canvas`; ранние запросы объединяются и выполняются после появления карты. Список modulepreload больше не используется для принудительного импорта.

Контракт endpoint проверен по текущему [публичному клиентскому модулю Wplace](https://wplace.live/_app/immutable/chunks/BsiAA4oX.js) и [публичной конфигурации](https://wplace.live/_app/env.js). Персональные API-запросы для этой проверки не выполнялись.

## Почему предыдущая проверка пропустила ошибки

Fixture готового userscript возвращала успешный ответ пользователя для любого URL и не моделировала последовательность загрузки настоящих ES-модулей Wplace. Это недостаток предыдущей приемки: локальный успех не подтвердил интеграцию с живым сайтом.

Новая fixture возвращает данные только с правильного backend URL, а для остальных адресов — 404; проверяется заполнение счетчика. Новый startup browser test использует настоящий `TemplateManager.importJSON({})`, modulepreload и ES-модули, которые падают до инициализации locale. Проверяется отсутствие раннего импорта, исправность последующего native import и отложенное обновление карты.

## Последующее исправление Use last map click

После восстановления карты в той же вкладке воспроизведен следующий симптом: Wplace показывает выбранный пиксель, но окно координат Chromora оставляет поля пустыми и сообщает `Click the desired top-left pixel on the map first.`

Текущий публичный клиент Wplace вызывает `getPixelInfo()` по адресу `/s${season}/pixel/${tileX}/${tileY}?x=…&y=…`. Оба обработчика Chromora распознавали маршрут без номера сезона, поэтому ответ не попадал в кеш последних координат. В обработчик fetch и ApiManager добавлена поддержка `/s0/pixel/…`, `/s12/pixel/…` и других числовых сезонов. Проверки разрешенных хостов и точных путей сохранены.

Запросы координат получают возрастающий номер при отправке. ApiManager игнорирует ответ с номером не новее уже принятого, поэтому поздний ответ на предыдущий клик больше не заменяет последний выбор.

Новый браузерный тест соединяет настоящий fetch hook, postMessage, ApiManager и окно координат. Он проверяет автоматическое заполнение всех четырех полей, восстановление кнопкой Use last map click, повторное открытие окна, нулевые и граничные координаты, ответы в обратном порядке и сохранение исходного ответа для Wplace. Сеть в тесте изолирована; реальные пиксели не изменяются.

## Повторная проверка: граница окружения Tampermonkey

После сообщения «все еще не работает» выполнен еще один клик в существующей вкладке Wplace. Консоль подтверждает отправку сообщения для сезонного pixel endpoint, но лог приема `Recieved message` отсутствует; окно координат остается пустым. Это локализует оставшийся отказ после распознавания URL, на входе в обработчик сообщений.

В обработчике использовалось сравнение `event.source !== window`. Tampermonkey передает userscript свою обертку `window`; она отличается от настоящего Window страницы, который приходит в `MessageEvent.source`. Разделение окружений описано в [документации Tampermonkey](https://www.tampermonkey.net/documentation.php#api:unsafeWindow), а форма обертки приведена в [issue Tampermonkey #1558](https://github.com/Tampermonkey/tampermonkey/issues/1558). [Document.defaultView](https://developer.mozilla.org/en-US/docs/Web/API/Document/defaultView) возвращает окно соответствующего документа.

Исправлены четыре проверки в ApiManager и TemplateManager: источником принимается окно `document.defaultView`, с fallback на `window` при отсутствии defaultView. Проверка origin и схемы сообщения сохранена. Это также исправляет прием результатов обновления тайлов, перехода к шаблону и выделения области из того же окружения.

Предыдущие browser fixtures выполняли userscript с тем же объектом window, что и сайт, поэтому не выявляли дефект. Теперь userscript выполняется с отдельной оберткой window, а инъецированный код — в настоящем окне страницы. **До исправления исходный код и предыдущая CI-сборка воспроизводимо не заполняли координаты в этой проверке.** После исправления проверка проходит, включая Use last map click, повторное открытие, порядок ответов и отклонение сообщений от same-origin iframe, чужого origin и с `source: null`. Это модель разделения окружений; она не заменяет финальную проверку установленной копии в Tampermonkey.

## Проверка установленной копии — завершена

Пользователь заменил код Chromora в Tampermonkey новой сборкой. После перезагрузки той же вкладки Brave прием сообщений `me`, `tile` и `pixel` подтвержден консолью. Клик по карте определил Tile X/Y **1469, 661** и Pixel X/Y **237, 581**. Пользователь выбрал исходный `converted_12.png`; окно координат показало `Latest map pixel loaded`, все четыре поля содержали указанные значения. Пользователь подтвердил: «теперь работает».

Установка выполнена пользователем: инструмент запрещает доступ к странице расширения. PNG также выбран пользователем, поскольку автоматический выбор локального файла недоступен. Во время диагностики пиксели на карте не отправлялись и тестовый шаблон не создавался.

## Выравнивание иконок и ручка изменения размера

По следующему замечанию пользователя убрано принудительное смещение SVG сворачивания на −0,5 px по обеим осям, в том числе для свернутого состояния. В живой вкладке измерения до изменения подтверждали это смещение относительно центра кнопки. Иконки теперь используют центрирование кнопки без дополнительного сдвига.

У ручки изменения размера Color Filter удалены фон, рамка, скругление и тень в обычном состоянии, при наведении и во время изменения размера. Темы больше не возвращают декоративную рамку. Область захвата и индикация фокуса с клавиатуры сохранены.

Только для Frutiger Aero по дополнительному замечанию пользователя горизонтальный фильтр увеличен со 170 до 190 px; добавлен нижний padding. До изменения нижний ряд заканчивался практически на границе внутреннего блока, а область горизонтальной прокрутки выходила за нее. Дополнительная высота дает место обоим рядам, кнопке All и полосе прокрутки. В остальных темах высота горизонтального фильтра остается 170 px.
