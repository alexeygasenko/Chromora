# Аудит производительности и корректности обработки шаблонов

Дата: 23 сентября 2026. Проверены текущие рабочие версии `src/Template.js`, `src/templateManager.js`, `src/apiManager.js` и соответствующие вызовы в `src/main.js`. Production-файлы не изменялись. Пользовательские незакоммиченные изменения входят в проверяемое состояние.

## Методика и ограничения

- Статический анализ полного жизненного цикла: создание PNG-шаблона → chunked bitmap/buffer → отрисовка тайла → статистика → выбор пикселей в область.
- `diagnostics.mjs` исполняет текущие тела классов в Node v25.8.0 с моками браузерных API. Импорты удаляются только из временной строки в памяти; сами алгоритмы не переписаны. Тесты проверяют наблюдаемый неверный результат через assertions. Их статус BUG_REPRODUCED означает подтверждение существующего дефекта, а не исправление.
- `browser-diagnostics.mjs` исполняет текущие классы и настоящий `utils.js` в headless Microsoft Edge 153 на этой машине. Canvas, PNG-кодирование, декодирование и палитра настоящие. Playwright берется из отдельной временной установки, зависимости проекта не изменены. Браузер закрывается в `finally`.
- Браузерные замеры синтетические: один тайл 1000×1000, белый фон, подсветка выключена, логи отключены. Это не FPS реальной карты, не нагрузочное тестирование Wplace и не профилирование мобильного устройства. Cold/warm результаты различаются; параллельная активность машины влияет на время.
- Постоянная утечка памяти не доказана heap snapshot. Отсутствие `close()` и размеры выделяемых массивов отделены от предположений о native/GPU-памяти.

## Подтвержденные дефекты

### PERF-01 — P1: обычная проверка прозрачности удаляет непустые части шаблона

**Места:** `src/Template.js:321–339`, переход к пропуску chunk в `src/Template.js:158–170`; включение проверки по умолчанию в `src/templateManager.js:825`.

**Условия:** PNG с прозрачным фоном, отдельными непрозрачными пикселями и размером chunk до 1000×1000; обычная настройка «пропускать прозрачные тайлы» включена, агрессивный режим выключен.

**Причина:** проверка размножает изображение с фиксированными смещениями, затем уменьшает его до 10×10. Такая выборка не доказывает отсутствие непрозрачных пикселей. Пиксели между точками выборки исчезают; функция возвращает false для непустого chunk, после чего `createTemplateTiles` его не сохраняет.

**Реальное воспроизведение в Edge:** PNG 1000×1000 с единственным белым пикселем (500,500). `createTemplateTiles(1000, realPalette, true, false)` возвращает **0 chunks вместо 1**, хотя `pixelCount.total` равен **1**. Отдельная проверка также теряет пиксели (100,100) и (999,999). Пиксели (0,0), (5,5), (50,50) в том же тесте обнаруживаются: результат зависит от расположения.

**Последствия:** невидимые/потерянные части созданного шаблона и несогласованная статистика. Это не ожидаемая погрешность агрессивного режима: дефект проявляется в обычном режиме.

**Исправление:** точная проверка alpha исходного прямоугольника без уменьшения с потерями, желательно в уже прочитанном ImageData. Агрессивный approximation разрешать только в отдельно обозначенном режиме. Добавить regression fixtures с редкими пикселями по сетке, включая края.

### PERF-02 — P1: выделение области выбирает цвет нижнего перекрытого шаблона

**Места:** `src/templateManager.js:1424–1425`, `1533–1558` (порядок рисунка); `266–297`, `360–362`, `410–411` (порядок выбора и устранение дубликатов).

**Условия:** два включенных шаблона с разными цветами пересекаются на пустом пикселе; пользователь выбирает «все цвета шаблона».

**Причина:** отрисовка сортирует шаблоны по `sortID` и рисует старший последним. Выбор области использует исходный `templatesArray`/`templateOrder`, выбирает младший первым, после чего отбрасывает следующий пиксель на той же координате. Общей модели видимого верхнего пикселя нет.

**Воспроизведение:** нижний красный шаблон `sortID=0`, верхний зеленый `sortID=1`, один общий пустой пиксель. Видимый цвет — зеленый (ID 2); `findTemplatePixelRuns(..., {mode:'template'})` возвращает красный (ID 1).

**Последствия:** инструмент подготовки раскраски выбирает цвет, который не соответствует показанному пользователю шаблону. В режиме одного цвета также возможен выбор скрытого нижнего шаблона, если верхний другого цвета отфильтровывается до разрешения перекрытия.

**Исправление:** единая функция определения верхнего непрозрачного template pixel с одинаковым `sortID`/tie-break в draw и area selection; фильтровать цвет после разрешения перекрытия. Regression: прозрачный верхний пиксель, разные цвета, одинаковые sortID и исходный массив в ином порядке.

### PERF-03 — P2: позднее завершение старого рендера перезаписывает свежую статистику карты

**Места:** `src/templateManager.js:1489`, `1613`, `2181–2182`; независимые async обработчики в `src/apiManager.js:64`, `182`.

**Условия:** два параллельных рендера одного chunk завершаются в обратном порядке. Это возможно при нескольких fetch/refresh и разной длительности декодирования/обработки.

**Причина:** каждый завершившийся вызов без проверки версии записывает `pixelStateByChunk` и `pixelCount.correct`. Revision из refresh bridge не передается в `drawTemplateOnTile`, нет compare-and-commit по chunk.

**Воспроизведение:** старый ответ содержит правильный пиксель; его decode задержан. Новый ответ содержит пустой пиксель и завершается первым: state=2. Затем завершается старый: state становится 1. Последующее выделение возвращает **0 пикселей вместо 1** для актуальной пустой карты. Это детерминированный interleaving с Promise gate; Canvas-mocks не определяют исход этой гонки.

**Последствия:** устаревшие проценты готовности и неверное выделение области; обратный порядок цветов может ошибочно считать уже заполненный пиксель пустым.

**Исправление:** монотонная версия на tile/chunk, фиксируемая при начале запроса/рендера, и запрет устаревшего commit. Версия должна учитывать актуальность запроса, а не только порядок завершения декодирования. Для старого fetch вернуть его изображение допустимо, но общую статистику новой карты не менять.

### PERF-04 — P2: разные цвета вне палитры считаются совпадающими

**Места:** `src/templateManager.js:1993–1997`, `2128–2137`.

**Условия:** непрозрачный цвет шаблона не найден в LUT и непрозрачный цвет карты также не найден; например произвольные RGB или alpha, отсутствующий в LUT.

**Причина:** оба цвета получают ID `-2`, и сравнение `bestTileColorID == bestTemplateColorID` трактует их как одинаковые.

**Воспроизведение:** template pixel `0xff123456`, board pixel `0xffabcdef`; LUT не содержит оба. `pixelCount.correct[tile].get(-2)` равен **1 вместо 0**.

**Последствия:** неверные проценты готовности для Other и пропуск подсветки несовпадения, поскольку неизвестные цвета объединяются в один цветовой класс. Частота зависит от наличия таких пикселей в реальных PNG/ответах карты.

**Исправление:** `-2` — категория, а не идентификатор совпадающего цвета. Для unknown использовать сравнение RGBA/RGB с явно выбранной политикой tolerance/alpha либо не включать их в «правильно» и явно показывать неподдерживаемые цвета.

## Подтвержденные затраты и риски производительности

### PERF-05 — P2: полный 3× readback и безусловное копирование буфера на каждом тайле

**Места:** `src/templateManager.js:1491–1505`, `1540`, `1617`, `1893`; `src/apiManager.js:64`, `182`.

Размер выходного холста всегда 3000×3000 при штатном `tileSize=1000`, даже когда сам шаблон занимает один логический пиксель. `getImageData` копирует весь тайл, а каждый шаблон безусловно получает `.slice()`, включая режим без фильтров и подсветки.

**Зафиксированные размеры:**

| Объект | Шаблон 1×1 | Шаблон 1000×1000 |
|---|---:|---:|
| Readback всего тайла | 36 000 000 B | 36 000 000 B |
| Копия chunked32 | 36 B | 36 000 000 B |
| Текущее состояние пикселей | 1 B | 1 000 000 B |
| Существующий chunked32 шаблона | 36 B | 36 000 000 B |

Один полный рендер удерживает около **73 MB временных JS-буферов** в дополнение к постоянному буферу шаблона и графическим ресурсам. Это арифметика фактических размеров TypedArray, не измерение RSS. Восьми одновременным рендерам нужны до ~584 MB таких временных данных только для readback/clone/state. Фактический пик зависит от перекрытия времени жизни и GC. Ограничения concurrency в обработчике нет.

**Edge 153, реальная Canvas → PNG обработка:**

| Шаблон | Cold, ms | Последующие 3 вызова, ms |
|---|---:|---|
| 1×1 | 92.7 | 29.1 / 49.0 / 29.8 |
| 1000×1000 | 76.1 | 54.1 / 57.0 / 60.6 |

Выходной PNG в обоих сценариях — 182 600 B; итоговое изображение белое. Последовательности синтетические; cold для второго сценария уже после прогрева общего процесса и потому не сравним с самым первым cold. Эти цифры не экстраполируются напрямую на сетевую карту или FPS. Но время 1px-сценария и размер readback показывают высокую фиксированную цену на каждый затронутый тайл.

Отдельный Node CPU тест с моками Canvas: 216.96 / 219.41 / 206.05 / 213.62 ms на миллион логических пикселей. Здесь настоящий JS scan/copy и выделение/fill readback, но нет настоящего canvas draw/PNG; VM overhead и другой JIT-контекст означают, что эти цифры нельзя сравнивать с Edge как ускорение/замедление браузера.

**Рекомендации:** читать board в исходном масштабе 1000×1000 для статистики, ограничивать readback нужной областью, хранить логические цвета компактно, копировать chunk только при его изменении, ограничить параллельные декодирования/рендеры. Выходной холст 3× оставить там, где он нужен изображению. После изменений повторить реальные тесты и проверить pixel-perfect результат.

### PERF-06 — P2: fallback yield привязывает завершение обработки к animation frame

**Место:** `src/templateManager.js:2194–2199`; вызовы, например, `2140–2142`.

Если `scheduler.yield` недоступен, обработка ожидает `requestAnimationFrame`. В VM сценарий с удержанным callback оставляет render Promise pending; доставка единственного callback завершает его. В большинстве браузеров rAF приостанавливается в фоновых вкладках, поэтому тяжелый рендер/выделение на fallback-пути может удерживать большие буферы и ожидающий fetch до возвращения вкладки. Поведение background rAF документировано в [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame).

В измеренном Edge 153 `scheduler.yield` есть, поэтому эта ветка на нем не была активна; дефект условный для окружений без этого API. Это отдельная проблема от полностью отсутствующего timeout у fetch bridge, который рассматривается в build/security-аудите.

**Рекомендация:** yield через очередь задач (`setTimeout`/MessageChannel с подходящей политикой) либо race с timer при скрытом документе; учитывать AbortSignal и revision. Нужен браузерный regression именно без scheduler.

### PERF-07 — P3: нет детерминированного освобождения временных ImageBitmap

**Места:** `src/templateManager.js:1489`, `1602`, `1617`; `src/Template.js:80`, `249`; удаление runtime template в `src/templateManager.js:1186`.

После 20 последовательных draw диагностический mock зафиксировал **20 созданных временных bitmap, 0 вызовов close()**. Аналогично filtered bitmap создается прямо в аргументе drawImage и не сохраняется для освобождения; исходный bitmap при создании шаблона не закрывается.

`ImageBitmap.close()` освобождает графические ресурсы, что определено [MDN](https://developer.mozilla.org/en-US/docs/Web/API/ImageBitmap). Отсутствие close само по себе не означает вечную утечку: GC может освободить объекты. Подтверждено отсутствие контроля времени освобождения, а не неограниченный рост RSS. При больших/частых рендерах это усиливает пиковое потребление памяти.

**Рекомендация:** `try/finally` для временных bitmap, закрытие постоянных bitmap после завершения использующих их операций при удалении/reload шаблона. Не закрывать общий bitmap до окончания конкурирующих draw.

## Дополнительные возможности оптимизации, не отдельные подтвержденные инциденты

- `drawTemplateOnTile` дважды перечисляет ключи всех chunk каждого шаблона (`1432`, `1469`) и каждый раз сортирует шаблоны. Индекс tile→templates и кеш сортировки уменьшают цену на большой коллекции. На небольших наборах это может быть несущественно; отдельного профиля для сотен шаблонов нет.
- При загрузке даже маленького chunk создается новый Canvas 3000×3000 (`1794`), хотя readback использует фактический размер bitmap. Canvas с точными размерами уменьшит native allocation без изменения логики.
- `Template.js:234` превращает PNG Uint8Array в обычный Array перед base64: дополнительное выделение и boxing чисел. Можно передавать TypedArray напрямую, проверив контракт `uint8ToBase64`.
- Объемные `console.log` в draw/import/create выводят массивы шаблонов, ImageData и base64. Для production стоит добавить debug flag; удержание объектов DevTools и цена сериализации зависят от браузера, поэтому здесь это не названо доказанной утечкой.
- Общий подсчет цветов импортируемого изображения (`Template.js:380–405`) идет одним синхронным проходом, без yield. Для очень больших исходных PNG возможны long tasks, но численные замеры этого пути отдельно не выполнялись.
- Шаблоны в неотрисованных тайлах имеют неизвестное состояние и не включаются в `findTemplatePixelRuns`. Это ограничение текущего алгоритма; без продуктового требования загружать все тайлы области оно не классифицировано как баг.

## Что проверено положительно

- Пиксельный scan и построение групп подсветки отдают управление каждые ~4 ms работы; это полезная защита отзывчивости, хотя графические копии до scan остаются монолитными.
- Есть coalescing UI-событий статистики до одного события в 250 ms.
- Stencil cache ограничен 12 фазами при неизменном drawMult; оснований считать этот конкретный cache бесконечной утечкой нет.
- Area selection ограничивает возвращаемые пиксели и поддерживает AbortSignal; описанная ошибка относится к порядку перекрытия, а не отсутствию лимита.

## Артефакты и повторный запуск

- `diagnostics.mjs`, `results.json`, `diagnostics-output.json`: Node-моки, assertions и сырые результаты.
- `browser-diagnostics.mjs`, `browser-results.json`: реальные Canvas/PNG fixtures и замеры Edge.
- Запуск Node: `node audit/2026-09-23/performance/diagnostics.mjs`.
- Для браузерного сценария задать `AUDIT_PLAYWRIGHT_MODULE` абсолютным путем к установленному `playwright/index.mjs`, затем `node audit/2026-09-23/performance/browser-diagnostics.mjs`. Путь Edge указан явно в скрипте и при повторении на другой машине должен быть адаптирован.

Основной порядок исправлений: потеря непустых chunks → приоритет перекрытий при выделении → актуальность статистики → уменьшение графических копий и ограничение concurrency → unknown color и совместимый yield → детерминированное освобождение ресурсов.
